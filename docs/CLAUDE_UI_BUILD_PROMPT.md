# GROTEC FarmerOS: UI Design and Implementation Brief for Claude

## Your role

You are the senior product designer and front-end engineer improving the UI of an existing internal web application called **GROTEC FarmerOS**. Work directly in the existing React + Vite + TypeScript + Tailwind codebase. Design and implement a polished, production-minded CRM interface - not a one-off concept, marketing landing page, or generic AI-generated dashboard.

The product is an internal operating system for **Grotec Agro Products**, an organic agri-input manufacturer in Tamil Nadu, India. Its users serve farmers who buy organic bio-fertilizers, bio-inoculants, crop growth, and crop-protection products. The UI should quietly communicate trust, clarity, field practicality, and agronomic care.

This is a business tool used all day by telecallers, managers, relationship managers, and founders. It must feel calm and credible at 9 a.m. on a busy calling day, not flashy, futuristic, or “vibe coded.”

## The highest-priority screen: Agent calling workspace

The Agent workspace is the product’s most important screen. Treat it as a focused workbench, not a data table or generic CRM page.

### Core job

The agent must be able to complete this flow without losing context:

`Dial -> see farmer/customer context -> record outcome -> choose next action`

### Recommended desktop layout

Create a purpose-built, full-height desktop workspace with a sensible responsive fallback:

- **Persistent contextual header:** customer identity, primary mobile number, location, lead status, ownership context, and visible call-state indicator.
- **Main context column:** farmer profile, crop and acreage, location, source, concise notes, recent interactions, follow-up history, and relevant lead details. Information should be scannable, not a wall of cards.
- **Call control / outcome column:** clear primary dial action, call state (`Dialing`, `Ringing`, `Connected`, `Ended`, `Not Answered` as supported by the existing integration), elapsed time when available, notes, and the three outcome choices.
- **Supporting reference panel:** Knowledge Base lookup that can be opened during a call without destroying the call context. Search by crop or problem and show the recommended Grotec product reference and high-level usage guidance.

### Interaction requirements

- Do not require agents to type phone numbers when dialing an existing customer.
- Make the exact three outcomes visually distinct and equally unambiguous: **Interested**, **Not Interested**, **Not Answered**.
- When **Interested** is selected, present a compact mandatory next-action dialog with exactly one choice: **Callback** or **Sales**.
- Callback must capture date, time, and reason/note. Keep the form compact, validate it clearly, and return the agent to their context after success.
- Do not create retry logic for Not Answered. The PRD leaves that decision open.
- Do not collapse outcome and next action into a single label in copy or UI.
- Use restrained status colors with text labels and icons; color must not be the only signal.
- Keep action hierarchy clear: dial/call state first, outcome second, secondary profile edits and history actions last.

The screen should enable a telecaller to work confidently at speed, even with modest computer hardware, intermittent attention, and a crowded call list.

## Other key experiences to improve

### App shell and navigation

- Retain the existing sidebar architecture and role filtering.
- Improve density, grouping, selected-state clarity, hover/focus feedback, and the visual hierarchy of the app identity.
- Use simple section labels and familiar icons. Do not overload the navigation with decorative badges.
- Make the user menu and sign-out control clearly accessible.
- On narrow screens, make navigation usable and reversible; never permanently trap content behind a fixed sidebar.

### Telecaller dashboard

The dashboard answers: **“Who do I need to contact today, and what is pending for each farmer/customer?”**

Prioritize today’s assigned calls, pending and overdue follow-ups, new leads, interested customers, converted customers, completed calls, reminders, and recent activity. For an agent, scope data to that agent’s workload.

Use a purposeful hierarchy:

1. A concise greeting/date and one useful action.
2. Follow-up queue, with overdue items unmistakable but not alarmist.
3. Small metric summary cards only where they support real decisions.
4. Recent activity and task-oriented secondary information.

Avoid a page filled with equally weighted KPI tiles. In particular, do not display invented revenue or sales figures.

### Customers and farmer profiles

- Design customer lists for rapid scan, filter, search, and follow-up.
- Treat phone-number duplicate prevention as a visible, helpful part of the customer-create/edit experience, not an obscure error after save.
- Make village, taluk, district, state, crops, acreage, history, notes, leads, and ownership easy to understand.
- Use farmer-centric labels such as “Farmer / customer,” “Crop details,” and “Location,” rather than forcing enterprise-sales jargon.
- The profile should clearly separate factual identity/contact details, activity timeline, crop context, and relationship ownership.

### Leads and follow-ups

- Show ownership, status, last interaction, next follow-up, and urgency at a glance.
- Use clear empty states that tell a user the next useful action.
- Retain a calm, legible chronological history. Do not make the user infer sequence from scattered cards.

### Relationship Manager workspace

Relationship ownership is distinct from lead ownership. Make that distinction understandable in the UI without exposing data-model terminology unnecessarily.

- Show assigned customers, relationship notes, follow-ups, and continuity history.
- Make ownership visible, traceable, and difficult to mistake for a free-for-all reassignment control.
- Do not fabricate an unapproved reassignment workflow.

### Knowledge Base

- Build a fast, typeahead-friendly crop/problem search pattern suitable during a live call.
- Support browse or search by crop, issue/problem, symptom keyword, and combined filters where current data supports it.
- Results should show the recommended Grotec product/brand reference and high-level usage guidance, with a clear indication that it is an internal reference.
- Use content states for no results, incomplete content, and permission-restricted editing.
- Management actions must appear only for permitted users. Agent users are view-only.

### Team, Audit, and administrative views

- Optimize tables for scanning and accountability: sticky or clear headers, appropriate row height, useful filters, readable empty states, and safe action affordances.
- Treat audit history as evidence: show actor, time, action, entity, and meaningful before/after values where available.
- Make high-risk actions visually deliberate. Avoid casual destructive icon-only controls.

## Visual design system

### Desired character

Aim for: **quietly modern Indian agri-business software** - grounded, clean, reliable, and human.

The interface should feel like a well-designed operations platform with small cues from agriculture: fresh growth, soil, field systems, trust, and real people. It must not look like a generic “green SaaS” template.

### Palette

Use a restrained, accessible system. Adapt existing Tailwind brand tokens rather than introducing uncontrolled one-off colors.

- Primary: deep leaf/forest green for brand, navigation, primary actions, and active states.
- Supporting: muted fresh green for success and selected background; warm soil/sand neutral for subtle visual depth; clean off-white surfaces; slate/charcoal text.
- Semantic colors: accessible green for success, amber for awaiting attention, red for destructive/error, blue or slate for neutral/in-progress states.
- Keep saturation modest. Reserve vivid color for high-priority state and primary action.

Suggested starting values, only if they fit the current token system:

```text
Forest: #166534 / #14532D
Leaf: #2F855A
Pale leaf: #DCFCE7
Soil: #A16207 or a low-saturation warm neutral
Canvas: #F8FAF7
Surface: #FFFFFF
Text: #172033
Muted: #64748B
Border: #E2E8E0
```

Verify contrast. Do not use color as the sole communication of outcome, validation, or urgency.

### Typography

- Use the current project font stack unless a simple, well-supported upgrade is already configured or can be made safely.
- Favor a legible sans-serif with strong numerals and good Tamil/Indian-language resilience if localization follows later.
- Establish a small, disciplined type scale. Page title, section heading, body, label, metadata, and table text should each have a consistent role.
- Avoid oversized “startup” headings, excessive all-caps, or cramped 10px body text.

### Layout and surface rules

- Use a spacing scale and consistent grid; do not hand-tune random margins throughout pages.
- Prefer a clear page frame: title/action row, optional summary, then the working content.
- Use cards only to group meaningful units of work. Avoid card-inside-card-inside-card layouts.
- Use 8-12px radius, subtle borders, and very soft shadows. The UI should feel engineered, not inflated.
- Dense operational tables and lists are welcome when hierarchy, alignment, and whitespace make them easy to read.
- Avoid gradients except for a very subtle, non-essential accent. Avoid glassmorphism, neon, giant floating blobs, excessive blur, or decorative “AI” imagery.

### Icons and imagery

- Continue using the existing Lucide icon system; use icons to reinforce, never replace, important text labels.
- Do not use stock photos of farmers as visual filler inside operational screens.
- If imagery is genuinely helpful for an empty state or onboarding, use a restrained, authentic agricultural illustration/photo treatment and keep it subordinate to the task.
- Do not generate fake product packaging, farm statistics, map data, or agronomic diagnoses.

## Interaction, quality, and accessibility bar

Treat this as production software.

- Make all user actions visible, predictable, and reversible when safe.
- Include loading, empty, error, offline/integration-failure, and success states for data-dependent UI.
- Use clear form labels, helpful inline validation, and meaningful error copy. No vague “Something went wrong” as the only feedback.
- Use native buttons/inputs or accessible equivalents; every interactive element needs keyboard access, focus visibility, and a sufficiently large target.
- Use semantic HTML and ARIA only where it adds real value.
- Support a minimum practical width for desktop operations and a clean responsive layout down to mobile. The Agent workspace may simplify/reflow on small screens, but must remain usable.
- Do not sacrifice readability for visual density. Avoid tiny text and low-contrast placeholder text.
- Respect `prefers-reduced-motion`; use motion sparingly and only to clarify state change.
- Preserve existing TypeScript strictness, linting, and tests. Do not silence type or lint errors with broad casts, `any`, or disable comments.

## Engineering guardrails

1. Keep the current architecture, routes, auth flow, API layer, and role permissions intact.
2. Do not add a large UI framework, animation library, or heavyweight chart package solely for decoration.
3. Do not hard-code business data that should come from existing APIs. Use realistic fallback/empty states only where the current page already needs them.
4. Do not add fake functionality, fake live integrations, or future-phase modules.
5. Do not expose confidential HR/payroll/salary information in this CRM codebase.
6. Do not change business terms: a telecaller/agent owns lead activity; a Relationship Manager owns the ongoing customer relationship after conversion. These are different concepts.
7. Do not add AI features; AI is not in the current CRM scope.
8. Do not make broad backend, schema, or dependency changes for a UI task unless essential, small, and justified.
9. Favor small composable components, typed props, and semantic class composition over one giant page component or a giant unstructured CSS file.
10. Do not alter source requirements or the reference documentation to justify UI choices.

## Delivery workflow

Work in deliberate increments:

1. Briefly audit the current UI and identify the most important consistency and usability gaps.
2. Establish or refine the shared visual language first: colors/tokens, typography roles, buttons, inputs, badges/statuses, tables, cards, dialogs, empty states, and page headers.
3. Apply the system to the shell and priority CRM screens, beginning with the Agent workspace.
4. Make responsive and accessible refinements.
5. Run the project’s relevant checks (`lint`, TypeScript/build, and tests available in this repository) and fix issues caused by your work.
6. Manually inspect the primary flows at desktop and narrow widths. Check visual rhythm, overflow, long farmer names, long locations, empty data, and visible focus states.

At completion, provide:

- A concise summary of what changed and why.
- A list of files changed.
- Checks run and their results.
- Any PRD/open-item limitations you intentionally preserved.

## Definition of done

The work is done when the existing GROTEC FarmerOS CRM looks like a coherent, thoughtfully designed product built for real agricultural customer operations:

- It has a clear farmer-first identity connected to Grotec’s organic, research-led, trust-based mission.
- It is clearly an internal operational CRM, not a public brochure site.
- The Agent workspace feels like the best screen in the product and supports the mandated calling flow without unnecessary navigation.
- Lists, profiles, follow-ups, ownership, and Knowledge Base search are fast to understand and use.
- Role boundaries, existing APIs, business rules, and current project scope remain intact.
- Visual design is modern but restrained, accessible, consistent, and maintainable.
- There are no fabricated data points, fake features, placeholder-heavy marketing elements, or generic “vibe-coded” dashboard patterns.
